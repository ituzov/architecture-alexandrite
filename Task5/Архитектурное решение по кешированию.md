# Архитектурное решение по кешированию

> **Задача 5:** повысить производительность MES-части, ускорить страницы и общий процесс обработки заказов.

---

## 1. Мотивация

*Нынешняя боль:* операторы жалуются на зависание страниц в MES, клиенты видят долгую обработку заказов.

**Почему кешировать?**
- **Снижение нагрузки на backend**: частые запросы к одним и тем же данным (список заказов, справочники) обслуживаются из быстрого кеша.
- **Ускорение UX**: данные на странице MES загружаются мгновенно.
- **Сокращение латентности бизнес‑процесса**: повторные чтения статусов заказа не дергают БД.
- **Экономия ресурсов**: меньше CPU/IO на MES API и базу.

**Метрики успеха:**
- Среднее время загрузки страницы MES ↓ 50 %.
- CPU MES API ↓ 30 %.
- Кол‑во запросов к Shop/MES DB ↓ 60 %.
- Lead‑time заказа ↓ 10 %.

---

## 2. Предлагаемое решение

### 2.1. Выбор уровня кеширования

- **Серверный кеш** предпочтителен, так как MES API централизует логику.
- **Клиентский кеш** (HTTP‑cache или browser storage) имеет смысл для справочников (статусы, настройки).

### 2.2. Паттерн кеширования

**Cache-Aside**

|                    | Cache-Aside                   | Write-Through       | Refresh-Ahead          |
|--------------------|-------------------------------|---------------------|------------------------|
| Легкость внедрения | + просто имплементация в коде | – сложнее в клиенте | – требует планировщика |
| Консистентность    | При шторме "холодных" miss    | + всегда актуальные | + всегда свежие данные |
| Нагрузка на БД     | пиковые случаи miss → DB hit  | нагрузка линейная   | равномерная нагрузка   |

**Почему Cache-Aside?**
- Прост в реализации в MES API.
- Позволяет контролировать момент инвалидации.
- Write-Through перегружает кеш при каждом update, а Refresh-Ahead сложно настроить и дорого держать scheduler.

### 2.3. Что кешируем

1. **Список заказов оператора** — ключ: `orders:list:userId`, TTL = 30 сек.
2. **Детали заказа** — ключ: `order:{orderId}`, TTL = 5 мин.
3. **Справочники** (статусы, типы заказов) — TTL = 24 ч, инвалидация по ключу при обновлении.

### 2.4. Стратегия инвалидации

- **Временная (TTL)** для списков и деталей.
- **По ключу** для справочников — при изменение в CRM API сбрасываем соответствующий ключ.
- **Программная**: при изменении статуса заказа (MES API → DB) инвалидаем `order:{orderId}` и сбрасываем список операторов.

## 4. Альтернативные стратегии и сравнение

| Стратегия     | Преимущества                   | Недостатки                          |
|---------------|--------------------------------|-------------------------------------|
| Cache-Aside   | Простота, контроль инвалидации | В пике cold‑miss нагрузка на БД     |
| Write-Through | Данные всегда актуальны в кеше | Высокая нагрузка на кеш при write   |
| Refresh-Ahead | Постоянно обновлённые данные   | Сложность scheduler, лишние запросы |

**Вывод:** Cache-Aside даёт баланс простоты и эффективности для наших сценариев.

---

## 5. Результат для бизнеса

- Страницы MES работают быстро, сокращается время ожидания оператора.
- Меньше запросов к базе, ресурсного экономия и стабильность.
- Lead‑time заказа падает, клиенты довольны скоростью обработки.
