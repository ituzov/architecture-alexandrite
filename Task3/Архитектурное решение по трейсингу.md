# Архитектурное решение по трейсингу (финальная текстовая версия)

> **Задача:** заказ иногда «висит» или теряется. Нужна сквозная видимость, чтобы за 1‑2 минуты понимать, где сбой, а не собирать логи часами.

---

## 1. Мотивация (зачем тратить время и деньги)

| Боль                                     | Что даст трейсинг                                                       | Измеряемый эффект          |
|------------------------------------------|-------------------------------------------------------------------------|----------------------------|
| Заказ «залип» на одном статусе           | Открываем трейс → видим точный сервис и причину (очередь, БД, тайм‑аут) | **MTTR** ↓ в 3‑5 раз       |
| Клиенты ловят 500‑е, а в логах пусто     | Трейс содержит span с stack‑trace и git‑SHA                             | **% повторных тикетов** ↓  |
| Lead‑time заказа вырос, но непонятно где | Корневой span показывает самый долгий шаг                               | **Lead‑time** ↓ на 10‑15 % |
| Сложно спорить с внешними партнёрами     | Спан внешнего API фиксирует их реальное время                           | **Соблюдение SLA** ↑       |

---

## 2. Где потенциально «ломается» — покрываем трейсингом

1. **Shop SPA → Shop API** — пользователь оформляет заказ.
2. **Shop API → RabbitMQ → CRM API / MES API** — доставка событий.
3. **CRM API ⇄ Shop DB** — подтверждение, закрытие.
4. **MES API ⇄ MES DB** — производство, упаковка, отправка.
5. **CRM/MES API → RabbitMQ → Shop API** — обратные статусы.
6. **S3‑хранилище** — загрузка/чтение 3D‑файлов.

---

## 3. Что кладём в каждый span

| Поле            | Пример      | Для чего                  |
|-----------------|-------------|---------------------------|
| `traceId`       | `a1b2‑…`    | Склеиваем цепочку         |
| `orderId`       | `ORD‑10452` | Фильтр по заказу          |
| `currentStatus` | `PACKAGING` | Видно, на чём остановился |
| `service.name`  | `mes‑api`   | Чья зона ответственности  |
| `duration_ms`   | `450`       | Находим bottleneck        |
| `error` + stack | `true`      | Причина сбоя              |
| infra‑лейблы    | pod, node   | Линк с k8s/EC2            |

## 4. Предлагаемое техническое решение и новые элементы

| Компонент                     | Технология / тип                                                         | Зачем нужен                                                        | Как внедряем / дорабатываем                                                                                                    |
|-------------------------------|--------------------------------------------------------------------------|--------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------|
| **OpenTelemetry SDK / Agent** | Java (otel‑java‑agent), .NET (OpenTelemetry.Instrumentation.*), Web OTEL | Автоматически собирает спаны/метрики из кода без правки исходников | Добавляем зависимость, включаем через JAVA_TOOL_OPTIONS / env vars; фронт — инициализация OTEL‑JS SDK.                         |
| **Trace‑Context**             | W3C `traceparent` + AMQP headers                                         | Сквозная корреляция HTTP и RabbitMQ‑сообщений                      | Либы OTEL делают это «из коробки»; в RabbitMQ — custom HeaderPropagator.                                                       |
| **OpenTelemetry Collector**   | Docker, DaemonSet в K8s                                                  | Принимает спаны/метрики, буферизует, делает batch и ретраи         | Helm‑chart `open-telemetry/opentelemetry-collector`. Конфиг: OTLP receiver, batch + queued_retry, Tempo exporter.              |
| **Grafana Tempo**             | TSDB для трейсов (object‑storage backend)                                | Дешёвое и масштабируемое хранение трейсов                          | Yandex K8s StatefulSet + MinIO/S3 backend.                                                                                     |
| **Grafana**                   | OSS 8.x                                                                  | UI для просмотра трейсов + правило‑based alerting                  | Helm‑chart `grafana/grafana`, связь с Tempo datasouce. Создаём дашборды Golden Signals и Rule‑alerting по длительности заказа. |
| **On‑Call Team (актёр)**      | Пачка + PagerDuty                                                        | Получают алерты 24/7                                               | Grafana → Webhook в Пачка #alerts; Grafana → PagerDuty API.                                                                    |

## 5. Компромиссы

| Риск                         | Что плохо             | Как смягчаем                                 |
|------------------------------|-----------------------|----------------------------------------------|
| Много спанов при высоком RPS | Дорого хранить        | 10 % sampling для 2xx, 100 % для 5xx         |
| Legacy‑код без OTEL          | «Слепые» зоны         | Инструментируем только критичный код вручную |
| Collector ↔ Tempo по сети    | Потери пакетов        | Включаем локальный кэш и ретраи              |
| S3‑SDK проприетарный         | Нет готового экспорта | Пишем лёгкий wrapper‑proxy                   |

---

## 6. Безопасность

- **mTLS** между Collector‑ами и Tempo.
- **SSO + RBAC** в Grafana (roles: viewer, support, admin).
- **NetworkPolicy** — Grafana и Tempo доступны только внутри VPC.
- **PII‑маска** в Collector (hash email/phone).
- **Аудит‑логи** Grafana/Tempo стекаются в Loki, retention 30 дней.

---

## 7. Авто‑алертинг по пути заказа (опция)

- Каждые 5 мин Grafana‑rule ищет трейсы, где **root‑span > 1 ч** или **нет `MANUFACTURING_STARTED` 30 мин**.
- При срабатывании: Пачка #orders + PagerDuty; HPA поднимает ещё один MES‑worker, если очередь растёт.

---

## 8. Результат для бизнеса

- MTTR падает с часов до минут, меньше простоя продаж.
- Процесс заказа прозрачен, видно узкие места → планомерно снижаем Lead‑time.
- Саппорт быстрее отвечает клиентам, потому что видит реальную причину сбоя.
- Инвестиции — два спринта + объём S3; все компоненты open‑source.
