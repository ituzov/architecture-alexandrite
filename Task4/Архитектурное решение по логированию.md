# Архитектурное решение по логированию

> **Задача 4:** централизовать сбор логов, чтобы разработчики и поддержка быстро находили причину проблем без «расспросов» клиентов.

---

## 1. Мотивация

| Боль                                   | Что даст логирование                           | Метрика эффекта               |
|----------------------------------------|------------------------------------------------|-------------------------------|
| Поддержка копается по словам клиента   | Логи показывают время, userId, orderId, action | MTTR ↓ в 2–3 раза             |
| Нет видимости аномалий и всплесков     | Агрегация логов + алерты по rate/spike         | Время обнаружения инцидента ↓ |
| Много точек сбоя во множестве сервисов | Полный контекст (pod, node, service) в логах   | Время диагностики ↓           |
| Нет единого поиска по логам            | Централизованная ELK/OpenSearch UI             | Удовлетворённость Support ↑   |

---

## 2. Анализ и идентификация источников логов

1. **Shop API**: операции заказа (INFO: `OrderCreated`, `StatusChanged`).
2. **CRM API**: подтверждение/закрытие заказа.
3. **MES API**: приём в работу, упаковка, отгрузка.
4. **RabbitMQ** (broker): publish/consume событий.
5. **S3 Storage**: загрузка 3D моделей.
6. **Аутентификация**: успех/неуспех login, token refresh.

### Уровни логирования
- **INFO** (основные события) — см. список выше.
- **ERROR** (исключения, тайм‑ауты) — stack‑trace, traceId.
- **WARN** (необычные, но не фатальные состояния).
- **DEBUG** — в dev/release, для payload‑ов и заголовков.

---

## 3. Приоритизация внедрения

Нельзя сделать всё сразу — начинаем с критичных участков:

1. **Shop API + RabbitMQ** — путь заказа от клиента → очередь.
2. **MES API + Shop DB** — где чаще всего залипают статусы.
3. **CRM API + MES DB** — для полного E2E.
4. **S3 и Auth** — файлы и безопасность.

## 4. Предлагаемое решение

Опишите, как и какими технологиями будет реализовано логирование:

| Компонент          | Технология      | Применение и доработка                                         |
|--------------------|-----------------|----------------------------------------------------------------|
| **Logback/Log4j2** | Java сервисы    | JSON‑вывод, MDC: `orderId`, `userId`, `pod`, `node`, `service` |
| **Serilog**        | .NET MES API    | Sink → HTTP/OTLP к collector                                   |
| **Pino / Winston** | JS frontend     | Консоль → FluentBit (JSON)                                     |
| **FluentBit**      | Log shipper     | Сбор Docker/K8s логов, добавление метаданных, парсинг JSON     |
| **Fluentd**        | Aggregation     | Фильтрация, трансформация, шипинг в Elastic/OpenSearch         |
| **Elasticsearch**  | Хранилище логов | Индексы `logs-<service>-YYYY.MM.DD`, rollover по size/time     |
| **Kibana**         | UI & алерты     | Поиск, дашборды, watcher‑alerting на rate-спайки и error-rate  |

---

## 5. Политика безопасности и работы с PII

- **PII‑masking**: email, phone хешируются на этапе Fluentd/Collector.
- **RBAC**: доступ к Kibana/OSD только у доверенных групп.
- **TLS**: шифрование канала shipper→ Elasticsearch/OpenSearch.
- **Audit‑логи**: кто и когда смотрел логи, хранение 90 дн.

---

## 6. Политика хранения и ретеншн

- **Индексы:** `logs-shopapi-YYYY.MM.DD`, `logs-mesapi-…`, etc.
- **Rotation:** rollover при достижении 10 GB или 1 дня.
- **Retention:** 30 дней активного хранения, архив в S3 Glacier на 1 год.

---

## 7. Анализ логов, алертинг и обнаружение аномалий

1. **Alerting:**
    - **Error rate** > 1 % от RPS за 1 мин → Пачка #alerts
    - **Spike rate**: `OrderCreated` sudden > ×10 за 1 мин → DDoS‑alert
2. **Anomaly detection:**
    - OpenSearch ML job на deviation по latency и rate
    - Kibana Lens для визуализации трендов и выбросов
